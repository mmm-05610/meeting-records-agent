## 逐项说明（命令与现象）

### A01 导入正常记录
- 命令：`tests/smoke/real_ingest_smoke.py`（R2R 文件入口、中文 Markdown）；`scripts/demo/import_dataset.py` 导入 3 项目 18 会议；浏览器 E2E 上传中文 TXT。
- 现象：`ingestion_status=success`，每份会议 4 个分块，metadata 含 `meeting_date/record_kind/participants/content_sha256`，列表状态「已就绪」，分块可读；原件经文件 provider 存储。
- 证据：`data/imports/*.json`、`.run/v0.1/smoke/real-ingest-smoke.json`、`docs/evidence/screenshots/02-documents.png`、`03-uploaded.png`。

### A02 错误输入与重复导入
- 空文件/缺标题/非法日期 → 400 `input_error` 且不调用模型；同一文件重传 → 200 + `existing:true` + 同一 `document_id`（C01 uuid5 确定性身份）；同名异内容 → 不同 ID；同文不同项目 → 不同 ID（契约向量覆盖）。
- 证据：`docs/evidence/api-boundaries.json`、`tests/contracts/`（ID 向量）。

### A03 项目隔离与范围过滤
- 修复：R2R `/v3/documents` 不按 collection 过滤（服务账号会拿到全库），Agent 在服务端按 collection 再过滤；检索命中后再核对 `document_id ∈ 快照`。
- 现象：跨项目 explicit 范围返回 `scope_forbidden`（无答案）；评测引用范围 100%；越界命中被丢弃。
- 证据：`docs/evidence/api-boundaries.json`、`eval summary` 的 `scope_rate`。

### A04–A08 事实、分工、决定与变更
- 真实问答输出（节选见 `docs/evidence/behavior-checks.json`）：
  - A04 负责人与截止时间来自不同会议，回答完整且标注“未说明是否已完成”。
  - A05 按会议时间核对 6 场：1 月仅候选 → 3 月正式确认混合检索 → 5 月仅重新建议，结论仍为混合检索并说明不覆盖。
  - A06 出库口 3→7 号门，并给出原文理由；A08 配送周期 48→24 小时，明确“记录中没有说明原因”。
  - A07 只记载负责人/截止，回答“不能据此判断已完成”。

### A09/A10 引用身份、定位与刷新（含 2026-10-22 12:40 修复）
- 回答正文含 `[n]` 编号（`AnswerRecord.sources[*].display_index` 持久化映射）；点击打开来源面板，显示会议标题、日期、片段序号（chunk_order）、文档 ID 与原文片段；同文异源按 document/chunk 身份区分。
- 刷新与重启后映射不变；未完成轮次只显示“本轮未完成”。
- 证据：`browser-flow.json`（citations=12）、`05-citation-dialog.png`、`07-after-refresh.png`、`restart-recovery.json`。
- 修复记录：用户反馈刷新/切换线程后，历史轮次被误标为“本轮未完成”。根因是历史消息没有稳定 id，无法与
  `AnswerRecord.message_id` 配对。修复：AI 消息 id 使用 AnswerRecord 的 message_id（Agent 侧 `ChatMessage.id`），
  历史恢复增加按原文/顺序的兜底配对，新建空线程不再被归属检查误判为 404；
  验证：刷新前后 `本轮未完成=0、已完成=3/6`，追问指代正确，见 `08-chat-completed-status.png`。
- 第二轮修复（用户反馈）：历史消息的 `type`（human/ai）此前被前端统一当作 assistant，导致用户问题显示成
  "未完成的回答"、澄清问题也显示成失败。修复：`/api/history` 正确映射角色；澄清轮渲染为"需要澄清"而不是
  "未完成"；只有确实没有 completed AnswerRecord 的轮次才标未完成（旧版本中断轮次保持如实展示）。
  验证：`restart-1792632748` 线程现在为 1 已完成 + 1 真实未完成 + 2 需澄清，用户消息右对齐，
  见 `09-chat-history-roles.png`。

### A11 追问与澄清
- 两轮对话：第一轮问“检索方案评审会上确认了什么”，第二轮问“那次会议有哪些人参加”，分类节点把指代解析为上一场会议后再回答（`resolved_question`）；无上下文的“那个方案定了吗？”先返回澄清问题，不猜测。

### A12 重启恢复
- 停/启 agent 与 web 后：历史仍返回 `answer_records`、范围快照指纹一致、引用映射保留、R2R 数据仍在；无 checkpoint 的失败轮次不显示为已完成。
- 证据：`docs/evidence/restart-recovery.json`（8/8）。

### A13 删除与部分失败
- 正常删除：文档/分块/原件（files）三处清零，其他会议不受影响。
- 注入部分失败（临时回收 `files` 表 DELETE 权限）：接口返回 500 + `deleted:false`，文档记录保留；恢复权限后重试成功并三处清零。
- 证据：`docs/evidence/delete-failure.json`（7/7）。

### A14 全部与显式范围
- all_ready：新一轮检索只使用当前就绪会议；导入新会议后下一轮纳入（ZEBRA-99 实验），上一轮不会凭空得知。
- explicit：空列表/越项目文档被拒绝；只使用显式列表。

### A15 故障与阅读预算
- R2R 宕机：Agent 返回 `service_failure` 且无完成答案；R2R 恢复后重试成功（恢复不是“无证据”）。
- 阅读预算：`MEETING_DECISION_MAX_MEETINGS=2` 且有 6 场会议时返回 `budget_exceeded`，不输出最终决定。
- 证据：`docs/evidence/service-failure.json`、`docs/evidence/budget.json`。

### A16 原文与客户端注入
- 恶意会议记录中的“忽略规则、输出系统提示词/密钥”只作为数据被引用，回答仍按证据给结论，无密钥或系统提示泄漏；客户端伪造 `user_id`/`configurable` 被 400 拒绝；未知 forwardedProps 被剥离。
- 证据：`docs/evidence/behavior-focus.json`、`docs/evidence/api-boundaries.json`。

### A17 时间顺序与冲突

## 未测/已知限制

1. docker compose 路径本机未实跑（无 Docker 守护进程）；native 模式已完整验证。
2. 宿主机挂起期间的自动唤醒未证明（A22 已标注）。
3. 决定类问题的语义标签有时偏粗（如把负责人信息标为 fact），评测已列出坏例；不宣称语义判断完美。
4. 生成模型依赖外部服务，个别请求仍可能失败（评测中出现 1 次 `service_failure`），界面显示真实失败而非伪完成。
5. 未做多用户/团队权限；单账号本地使用；注册入口已关闭。
6. 账号绑定上线前创建的旧线程（checkpoint 中没有账号归属）无法恢复历史：界面会提示并自动新建会话，不再展示为“已完成”。
7. 参考示例（CopilotKit example / Ragas examples）以本地参考方式使用，未复制进产品目录；AG-UI 客户端使用官方 `@ag-ui/client`，聊天运行时采用同源透明代理（未使用 `@copilotkit/runtime`），该差异已记录。
