# 第一阶段必须建立的夜间恢复检查

这是对 DeepSeek Harness 执行本次开发工作的要求，不是产品后台功能。本包未实际创建任何定时任务，也不预设 Harness 的命令语法。

## 时间与有效期

- 时区固定为 IANA `Asia/Shanghai`（北京时间 UTC+8），不能直接按执行机时区解释。
- 本次夜间窗口：01:30–09:30，两端包含，间隔 30 分钟。
- 完整时点为：01:30、02:00、02:30、03:00、03:30、04:00、04:30、05:00、05:30、06:00、06:30、07:00、07:30、08:00、08:30、09:00、09:30，共 17 次。
- 本包编制时预期窗口是 **2026-10-22**。启动时读取真实北京时间：当天尚未过 09:30 时使用当天剩余时点；已经过去的时点不补发。若实际启动已越过当天整个窗口，则使用下一天的同一窗口并记录选定日期。
- 只建立本次窗口的任务，不默认无限每日重复。最后一个时点后无后续触发；产品验收提前完成或用户取消时提前清理本次任务。
- 09:30 最后一次可以检查并恢复尚未完成的工作，但不杀死已经正常运行的任务；随后只结束调度窗口。开发是否继续由原 goal 和用户指令决定。

## 第一阶段的实际动作

1. 在正常目录/依赖/权限初始化时，先取得本项目根目录、当前 goal/会话身份和执行状态，保存最小可恢复信息。耗时依赖下载前就完成调度安排，避免下载中断后尚无恢复机制。
2. 检查是否已存在针对同一项目、同一 goal、同一窗口的恢复任务；存在则核对并复用，不重复创建。
3. 优先使用 Harness 已有、可持久化且不依赖当前工作轮次存活的调度及 resume 能力。若原生能力不满足，才使用已安装、已允许的系统调度器与已验证的 Harness 恢复入口。复用既有工具，不开发自定义守护进程/调度平台。
4. 实际创建调度，随后读取真实任务列表或配置，核对 ID、启用状态、时区、每个未来触发点、结束时间、工作目录和目标 goal。创建结果未知时先查已有任务再重试。
5. 记录去敏回执到 `.run/v0.1/scheduler-receipt.md`，明确调度是否能在当前工作会话退出/网络恢复后独立触发。只有会话内存活的 sleep 循环不满足要求。
6. 使用已验证的检查入口做受控验证：任务活跃时不重入；确认中断时可接续。不能只写一个计划文件，不能仅通知用户“该继续工作了”。

Harness 的实际 API 名称、调度表达式和恢复命令必须从其可用工具/帮助核实，不在本包里捏造 `/cron`、`dsh resume` 等命令。若可用调度机制无法满足半小时频率或持久恢复，记录具体限制并报告，不悄悄改为每小时，也不绕过权限。独立产品工作可继续，但 A21/A22 不可标 PASS。

## 每次检查做什么

```text
读取本次 goal、任务状态、Git 状态和 Harness 真实执行状态
  ├─ 用户取消 / 已验收完成 → 关闭本次后续触发并结束
  ├─ 同一 goal 仍活跃 → 记录检查，不启动第二个执行者
  ├─ 状态未知 / 上次操作结果未知 → 先查询实际状态，不重复变更
  └─ 已确认中断且可恢复 → 取得已有机制的排他执行权
       → 恢复原 goal/会话（必要时使用已验证的接续入口）
       → 对照 checkpoint、提交和未提交文件
       → 从依赖满足的第一个未完成任务继续
       → 保存新状态与证据
```

不能把“一次检查没有新输出”当作死进程；构建、下载、评测可能正常耗时。不得强杀仍活跃任务、清除不确定归属的锁或强制覆盖未提交文件。优先用 Harness 已有的活动状态和任务占用机制；系统互斥只采用现成能力，不新建协调数据库。

需要恢复时，接续原目标、任务账和目录。不得每半小时无条件启动一个新 `/goal`，不得把多次触发累积成多个并发开发者。若原会话无法恢复，只能使用 Harness 已验证的接续机制读取同一目标与状态，并保证旧执行者已停止。

## 中断点与副作用核对

每完成一个任务、产生提交、进入阻塞或开始高影响操作前，I 更新 `.run/v0.1/status.md`：

| 字段 | 内容 |
|---|---|
| goal / session | 当前目标与会话定位；仅本地保存 |
| window | 具体日期、Asia/Shanghai、任务 ID 和结束策略 |
| baseline / head | 输入版本、当前提交、未提交路径 |
| tasks | 各任务 PENDING/RUNNING/BLOCKED/DONE、所有者、依赖、完成证据 |
| active_operation | 正在执行的命令/请求及可查询标识，不保存密钥 |
| next_action | 恢复后的第一个具体动作 |
| resources | 本项目 Compose 名、端口、数据库、卷与占用者 |
| blockers | 缺什么、影响哪些任务、其他任务能否继续 |

工作者各写独立回执，由 I 汇总，避免并行覆盖总账。上传要查 document ID，迁移要查版本，容器要查实际状态，推送要查远端提交；超时不等于未执行。保留所有用户改动，不用 hard reset 或删除环境“重新开始”。

网络/API 短暂失败采用工具支持的有限退避并保存状态；恢复检查用于再次接续，不保证故障机器离线时仍能运行。预算、权限、凭据缺失与用户暂停不能被当作网络异常绕过。

## 恢复检查的任务正文模板

> 检查本项目的 v0.1 开发 goal 是否仍正常推进。先读取 `.run/v0.1/status.md`、当前 Git 状态、Harness 的真实活动状态和本次调度回执。如果用户已取消或 A01–A24 已完成，清理本次恢复检查并结束；如果同一 goal 正在运行，只记录检查，不重入；如果确认因网络、API 或进程异常中断，先核对上次操作是否已经完成，取得已有机制的排他执行权，接续原 goal，从 `specs/001-v0.1/tasks.md` 中依赖满足的未完成任务继续。保留未提交改动和已有证据，不重复导入、迁移或启动新目标。权限、凭据和预算阻塞据实报告，不绕过。窗口结束后不再建立新的周期。

## 清理与验收

保存创建、检查/受控恢复和关闭回执。清理只按本次登记 ID 操作，不能停用其他用户任务。最后回读确认无本次未来触发。A21 检查时间和持久调度，A22 检查实际恢复及不重入，A24 检查交付时清理。
